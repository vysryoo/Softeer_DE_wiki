# W6M1: 서울 따릉이 대여 데이터 수집 파이프라인 요구사항 (2조)

## 1. 프로젝트 개요
Airflow DAG 기반으로 서울시 공공 API(`tbCycleRentUseDayInfo`)에서 따릉이 대여 데이터를 수집 → 정제 → DB 저장 → 집계 → 품질 검사하는 파이프라인.
- **수집 대상 일자**: 2026-06-27, 2026-06-28
- **일별 예상 규모**: 약 10만 건 
- **대상 일자 관리**: 수집 대상 일자는 코드가 아닌 설정 파일(`config.json`)의 리스트 값으로 관리한다. 대상을 늘리거나 바꿀 때 DAG 코드를 수정하지 않는다.
- **특이 사항**: 세부적인 구현 방식은 각자의 재량에 맡긴다.

## 2. API 명세 (`tbCycleRentUseDayInfo`)

### 요청 인자
| 변수명 | 타입 | 필수 | 설명 |
|---|---|---|---|
| KEY | String | ✅ | OpenAPI 인증키 |
| TYPE | String | ✅ | 응답 형식 (`xml` / `json`) |
| SERVICE | String | ✅ | `tbCycleRentUseDayInfo` |
| START_INDEX | Integer | ✅ | 요청 시작 행 번호 |
| END_INDEX | Integer | ✅ | 요청 종료 행 번호 |
| RENT_DT | String | ✅ | 대여일자 (`YYYYMMDD`) |

### 출력값
| No | 출력명 | 설명 |
|---|---|---|
| 공통 | list_total_count | 총 데이터 건수 |
| 공통 | RESULT.CODE / MESSAGE | 요청 결과 코드·메시지 |
| 1 | RENT_DT | 대여일자 (YYYYMMDD) |
| 2 | RENT_ID | 대여소번호 |
| 3 | RENT_NM | 대여소명 |
    | 4 | RENT_TYPE | 대여구분코드 |
| 5 | GENDER_CD | 성별 |
| 6 | AGE_TYPE | 연령 |
| 7 | USE_CNT | 대여건수 |
| 8 | EXER_AMT | 운동량 |
| 9 | CARBON_AMT | 탄소절감량 |
| 10 | MOVE_METER | 이동거리(M) |
| 11 | MOVE_TIME | 이용시간(분) |
- `GENDER_CD`는 API가 대소문자를 섞어 내려줄 수 있으므로, 저장 전 대문자로 통일해 하나의 값으로 취급하기로 합의했다.

## 3. 수집 & 페이지네이션

Offset(시작·끝 인덱스) 방식으로 수집한다.
- 1회 호출당 **최대 1000건** (API 자체 제한)
- START_INDEX를 **1000씩 증가**시키며 `list_total_count`에 도달할 때까지 반복
- 두 날짜(06-27, 06-28)의 모든 페이지를 빠짐없이 수집
- **호출마다 로그를 기록**
- **수집 건수 검증**: 모든 페이지를 합친 실제 행 수가 API가 응답한 `list_total_count`와 다르면 수집 실패로 간주한다. 
- API가 HTTP 200을 반환해도 응답 본문의 `RESULT.CODE`가 정상 코드(`INFO-000`)가 아니면 실패로 간주한다 (HTTP 상태코드만으로는 API 자체 오류를 걸러낼 수 없기 때문).

## 4. DAG 처리 흐름
두 날짜(06-27, 06-28)는 하나의 DAG 실행 안에서 날짜별로 독립적으로 처리되며, 저장까지 끝난 뒤에만 집계·품질검사 단계에서 합류한다.
```
[날짜별 독립 처리]
① 데이터 수집 (API 호출 + 건수 검증)
② 데이터 정제 + 정제 검증 (검증 실패 시 이 단계 안에서 재수집 반복, 최대 2회)
③ Raw / 정제 데이터 DB 저장
        ↓ (두 날짜 모두 ③까지 끝나야 진행)
[전체 합류 처리]
④ 집계 데이터 DB 저장 (대여소 단위 통계 계산)
⑤ 데이터 품질 검사 (샘플 재검증 + 건수 비교 + 스키마 비교)
```
- 정제 검증 실패 시 DAG 그래프 상에서 앞 단계로 되돌아가는 대신 **정제 task 내부에서 재수집을 자체적으로 반복**하는 방식 
  (Airflow task 간 역방향 이동은 표준적인 방식이 아니고, 실패/재시도 이력 추적이 더 명확하기 때문)
- 재수집 한도(기본 2회)를 다 써도 검증에 실패하면, 그 시점에 DAG를 실패시킨다.
### Task 정의 기준
- 알림을 받고 싶은 작업 단위
- 작동 시간을 측정하고 싶은 작업 단위

## 5. 재시도 & 실패 정책
| 단위 | 정책 |
|---|---|
| **API 요청(페이지 호출)** | 실패 시 최대 2회 재시도, 재시도 간격 5초 |
| **Task** | 최대 3회 재시도, **지수 백오프**(1분 → 2분 → 4분 상한) |
| **정제 검증 실패** | 수집 단계로 되돌아가지 않고, 정제 task 내부에서 최대 2회까지 재수집 반복 |
| **재시도/재수집을 모두 소진해도 실패** | DAG 실행을 실패 상태로 종료 |
| **실패 알림** | 자동 재트리거는 하지 않는다. 실패 사유를 알림 로그 테이블에 기록하고, 운영자가 이를 확인한 뒤 수동으로 DAG를 재실행한다 |
- "고정 간격 vs 지수 백오프" 검토 항목은 **지수 백오프**로 최종 결정했다.
- "10분 후 자동 재호출" 방식은 채택하지 않고, **로그 기반 알림 + 운영자 수동 재실행**으로 합의했다.

## 6. 스케줄링 & 설정
| 항목 | 값 |
|---|---|
| schedule | `None` (수동 트리거) |
| start_date | 고정값 지정 (schedule=None이라 실질적 의미는 없으나 DAG 정의상 필수) |
| catchup | `False` |
| max_active_runs | `1` (동시 실행 방지, 멱등성 보장) |
| execution_timeout | 날짜별로 반복되는 수집/정제 task는 **15분**, 그 외(저장/집계/품질검사) task는 **5분** |
| SLA | 집계·품질검사 task **5분** |
- 원래 "Task별 1분" 검토안은, 대량 API 호출(날짜당 최대 100회 호출)이 걸리는 수집/정제 task와 짧게 끝나는 저장/집계/검사 task의 소요 시간이 크게 다르다는 걸 확인하고 **task 성격별로 다른 타임아웃**을 두는 것으로 조정했다.

## 7. 네트워크 처리
- HTTP 오류(4xx/5xx) 처리
- 타임아웃: **15초**
- API 재시도 횟수: **2회**
- 재시도 간격: **5초**
- 응답 본문 구조가 기대와 다르거나(`row`/`list_total_count` 필드 부재), API 자체 오류 코드가 내려오는 경우도 동일하게 실패로 간주해 재시도 대상에 포함한다.

## 8. 데이터 정제 규칙
### PK 결정
- 기존 속성으로는 고유하게 행을 구분할 수 없어서 새롭게 인공키를 만드는 것으로 합의.
### 핵심 속성 처리
- RENT_DT, RENT_ID, RENT_TYPE, AGE_TYPE 이상치거나 결측치이면 행 자체를 저장하지 않는다.
### Null로 변환 후 저장 (로그 기록)
- 측정 컬럼(`USE_CNT, EXER_AMT, CARBON_AMT, MOVE_METER, MOVE_TIME`)의 음수 값 → NULL 처리 (행은 유지)
- 측정 컬럼의 숫자 변환 실패 값 → NULL 처리 (행은 유지)
- PK가 아닌 컬럼의 결측 → NULL로 저장
### 값 판정 기준
| 값 | 정상 컬럼 | 비정상 컬럼 |
|---|---|---|
| **0 값** | 이동거리, 대여건수, 이용시간, 탄소절감량 (측정 컬럼) | 대여일자, 대여소번호 (PK 컬럼) |
- 최초 검토안에는 "나이"도 0 값 비정상 컬럼으로 포함되어 있었으나, 연령대는 텍스트 값이어서 판정 대상에서 제외하기로 최종 합의했다.

## 9. 데이터 품질 검사
- 정제된 데이터에 대해 수행
- **전수 검사 대신 5% 샘플링**: 이미 정제된 데이터에서 5%를 뽑아 동일한 정제 규칙을 다시 적용해 보고, 이번에도 걸러지는 행이 있으면(위반) 정제 로직 자체에 문제가 있다는 신호로 본다.
- **RAW vs 정제 데이터 총 건수 비교**: 대여일자 단위로 두 테이블의 행 수 차이를 계산해 정제 단계에서 사라진 행 수와 대략 일치하는지 확인한다.
- **스키마 검증**: 최종 저장 테이블(정제 테이블, 집계 테이블)에 필요한 컬럼이 모두 존재하고 타입이 기대와 같은지 확인한다.
- **실패 처리 기준**: 샘플 재검증 위반 건수가 허용치를 넘거나, 스키마 검증이 하나라도 실패하면 파이프라인(DAG) 전체를 강제 실패로 처리한다.
- 허용치와 강제 실패 여부는 설정값으로 관리해 이후 기준을 조정할 수 있게 한다.
